01Race condition: ví dụ mất cập nhật

Kho còn 10 chiếc áo. Hai khách bấm mua cùng lúc, mỗi request làm ba bước: đọc tồn kho, trừ 1, ghi lại.

// Read-modify-write in application code: unsafe under concurrency
async function buy(productId: string) {
  const { rows } = await db.query("SELECT stock FROM products WHERE id = $1", [productId]);
  const stock = rows[0].stock;              // both requests may read 10 here
  if (stock <= 0) throw new Error("Sold out");
  await db.query("UPDATE products SET stock = $1 WHERE id = $2", [stock - 1, productId]);
}
Lỗi này không phải do JavaScript đa luồng. Node.js chạy một luồng, nhưng mỗi await nhường chỗ cho request khác chen vào giữa bước đọc và bước ghi. Chạy nhiều instance hay nhiều pod thì càng dễ xảy ra.

03Isolation level của database

Database tự chống một phần các lỗi trên, tùy mức cô lập (isolation level) của transaction. Mức càng cao càng an toàn nhưng càng nhiều xung đột phải retry.

MứcDirty readNon-repeatablePhantomGhi chú
Read UncommittedCó thểCó thểCó thểPostgreSQL xử lý như Read Committed

Ở mức mặc định Read Committed, ví dụ mua áo ở trên vẫn bị lost update. Muốn an toàn phải dùng thêm lock hoặc câu lệnh atomic, xem tab Lock trong DB.

04Blocking và non-blocking

Blocking

Gặp tài nguyên đang bị khóa thì đứng chờ tới khi được nhả. Đơn giản, đúng thứ tự, nhưng tốn kết nối và có nguy cơ deadlock, chờ lâu.

Non-blocking

Không chờ: thử lấy khóa, không được thì báo ngay (NOWAIT, tryLock), bỏ qua (SKIP LOCKED) hoặc làm rồi kiểm tra (optimistic, CAS). Phản hồi nhanh, nhưng phải xử lý trường hợp thất bại.

Ở giữa là chờ có giới hạn: lock_timeout trong PostgreSQL, timeout khi lấy distributed lock. Gần như luôn nên đặt giới hạn này.
