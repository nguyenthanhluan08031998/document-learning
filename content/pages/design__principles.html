Nguyên tắc trước, pattern sau

Design pattern là lời giải đã được đặt tên cho các vấn đề thiết kế lặp đi lặp lại. Chúng đều xuất phát từ vài nguyên tắc nền, quan trọng nhất là SOLID. Hiểu nguyên tắc thì tự nhận ra khi nào cần pattern, khi nào không. Chưa vững class, interface, kế thừa thì xem tab OOP trước.

01Pattern là gì, chia nhóm thế nào

NhómGiải quyếtSố lượng
CreationalCách tạo đối tượng mà không phụ thuộc lớp cụ thể5
StructuralCách ghép lớp và đối tượng thành cấu trúc lớn hơn7
BehavioralCách các đối tượng giao tiếp và chia trách nhiệm11
MicroserviceVấn đề khi hệ thống chạy trên nhiều service, qua mạngnhiều

23 pattern đầu đến từ cuốn Design Patterns (1994) của nhóm “Gang of Four” (GoF). Nhóm microservice được tổng hợp sau này từ kinh nghiệm xây hệ thống phân tán.

Đừng ép pattern vào code. Pattern có giá phải trả: thêm lớp, thêm gián tiếp. Viết đơn giản trước, khi thấy đau (sửa một chỗ phải đụng mười chỗ, khó test) thì mới tìm pattern phù hợp.

02Single Responsibility

Mỗi module chỉ nên có một lý do để thay đổi, tức là phục vụ một nhóm người dùng hoặc một mối quan tâm.

// Before: one class changes for business rules, SQL and email templates
class OrderService {
  create(o: Order) { /* validate + INSERT + send email */ }
}

// After: each part changes for its own reason
class OrderValidator { check(o: Order) { /* rules */ } }
class OrderRepository { save(o: Order) { /* SQL */ } }
class OrderMailer { confirm(o: Order) { /* email */ } }

03Open/Closed

Mở để mở rộng, đóng để sửa đổi: thêm tính năng bằng cách thêm code mới, không sửa code đã chạy ổn.

// Adding a new discount type means adding an object, not editing a switch
interface Discount { applies(o: Order): boolean; amount(o: Order): number; }

const discounts: Discount[] = [newCustomer, flashSale, voucher];
const totalDiscount = (o: Order) =>
  discounts.filter(d => d.applies(o)).reduce((s, d) => s + d.amount(o), 0);

Pattern liên quan: Strategy, Decorator, Observer, Template Method.

04Liskov Substitution

Lớp con phải thay được lớp cha mà không làm sai chương trình: không đòi hỏi thêm điều kiện đầu vào, không trả về ít hơn điều đã hứa, không ném lỗi bất ngờ.

class FileStorage { write(path: string, data: string) { /* ... */ } }

// Violation: callers of FileStorage do not expect write() to throw
class ReadOnlyStorage extends FileStorage {
  write() { throw new Error("read only"); }
}

// Better: model the capability explicitly
interface Readable { read(path: string): string; }
interface Writable { write(path: string, data: string): void; }

05Interface Segregation

Không bắt client phụ thuộc vào phương thức nó không dùng. Chia interface lớn thành nhiều interface nhỏ theo vai trò.

// Instead of one fat UserService interface:
interface UserReader { findById(id: string): Promise<User | null>; }
interface UserWriter { save(u: User): Promise<void>; }

// A report job only needs reading, so tests only mock one method
class ActivityReport { constructor(private users: UserReader) {} }

06Dependency Inversion

Module cấp cao (nghiệp vụ) không phụ thuộc module cấp thấp (database, HTTP); cả hai cùng phụ thuộc vào abstraction, và abstraction do phía nghiệp vụ định nghĩa. Đây là nền móng của Clean Architecture.

// Business layer owns the interface
interface PaymentPort { charge(userId: string, amount: number): Promise<string>; }

class PlaceOrder {
  constructor(private payment: PaymentPort) {} // depends on abstraction
  async run(userId: string, amount: number) { return this.payment.charge(userId, amount); }
}

// Infrastructure implements it; swap freely in tests
class StripePayment implements PaymentPort { async charge() { return "ch_123"; } }
const useCase = new PlaceOrder(new StripePayment());
