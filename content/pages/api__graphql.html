Sổ tay GraphQL: client hỏi đúng thứ cần

GraphQL là ngôn ngữ truy vấn cho API. Server công bố một schema có kiểu rõ ràng, client gửi query mô tả chính xác các trường muốn lấy và nhận về JSON có đúng hình dạng đó, qua một endpoint duy nhất.

query
{
order
{ id
total }
}

01GraphQL là gì

Với REST

Màn hình đơn hàng cần gọi /orders/42, rồi /users/7, rồi /orders/42/items. Mỗi endpoint trả nhiều trường thừa (over-fetching) mà vẫn thiếu dữ liệu nên phải gọi thêm (under-fetching).

Với GraphQL

Một request tới /graphql lấy đơn hàng, người mua và danh sách món, chỉ những trường màn hình cần.
# Request
query OrderPage($id: ID!) {
  order(id: $id) {
    id
    total
    customer { name }
    items { name qty }
  }
}
// Response
{
  "data": {
    "order": {
      "id": "42",
      "total": 350000,
      "customer": { "name": "An" },
      "items": [{ "name": "Phở", "qty": 2 }]
    }
  }
}

02Luồng xử lý một query

  1. Parse
    Chuỗi query được chuyển thành cây cú pháp (AST). Sai cú pháp thì dừng luôn.
  2. Validate
    So với schema: trường có tồn tại không, kiểu tham số đúng không. Lỗi ở đây thì không resolver nào chạy.
  3. Execute
    Đi theo cây query, mỗi trường gọi một resolver. Các trường cùng cấp trong query có thể chạy song song.
  4. Trả kết quả
    JSON gồm data và (nếu có) errors. Có thể vừa có dữ liệu vừa có lỗi.

03Schema & kiểu dữ liệu

type Order {
  id: ID!                 # ! means non-null
  total: Int!
  status: OrderStatus!
  customer: User!
  items: [OrderItem!]!    # non-null list of non-null items
}

enum OrderStatus { PENDING PAID SHIPPED }

input CreateOrderInput {  # input types are used for arguments
  items: [ItemInput!]!
}

type Query {
  order(id: ID!): Order
  orders(first: Int = 20, after: String): OrderConnection!
}

type Mutation {
  createOrder(input: CreateOrderInput!): Order!
}

type Subscription {
  orderStatusChanged(id: ID!): Order!
}
LoạiÝ nghĩa
ScalarInt, Float, String, Boolean, ID, và scalar tự định nghĩa như DateTime.
ObjectKiểu có các trường, ví dụ Order.
InputKiểu chỉ dùng làm tham số đầu vào.
EnumTập giá trị cố định.
Interface / UnionMột trường có thể trả nhiều kiểu, ví dụ kết quả tìm kiếm là Product | Shop.
List [ ] và Non-null !Mặc định mọi trường đều có thể null; thêm ! để bắt buộc có giá trị.

04Query, Mutation, Subscription

LoạiDùng đểGhi chú
queryĐọc dữ liệuCác trường gốc chạy song song.
mutationGhi, thay đổi dữ liệuCác trường gốc chạy tuần tự theo thứ tự viết.
subscriptionNhận sự kiện theo thời gian thựcChạy qua WebSocket (giao thức graphql-ws) hoặc SSE.
  • Variables ($id): tách giá trị động khỏi query, giúp cache và tránh ghép chuỗi.
  • Fragment: nhóm trường dùng lại nhiều nơi, ví dụ fragment OrderCard on Order { id total }.
  • Alias: lấy cùng trường hai lần với tham số khác: a: order(id: 1) { … } b: order(id: 2) { … }.
  • Directive: @include(if: $x), @skip(if: $x) ở client; @deprecated trong schema để đánh dấu trường sắp bỏ, thay cho việc đánh version.
  • Introspection: client hỏi được chính schema, nhờ đó có công cụ tự gợi ý như GraphiQL và sinh code.

05Resolver & bài toán N+1

Mỗi trường có một resolver nhận (parent, args, context, info). Resolver của orders trả về danh sách, rồi với từng đơn, resolver customer lại chạy một lần.

Cách viếtSố truy vấn DB cho 50 đơn hàng
Resolver customer gọi DB trực tiếp1 (orders) + 50 (mỗi customer) = 51
Dùng DataLoader gom các id trong cùng một nhịp1 (orders) + 1 (WHERE id IN (…)) = 2
DataLoader gom mọi lời gọi load(id) phát sinh trong cùng một tick, gọi DB một lần theo lô, rồi cache kết quả trong phạm vi một request. Tạo DataLoader mới cho mỗi request để không lẫn dữ liệu giữa người dùng.

06Lỗi, HTTP & cache

{
  "data": { "order": { "id": "42", "customer": null } },
  "errors": [{
    "message": "Customer service unavailable",
    "path": ["order", "customer"],
    "extensions": { "code": "UNAVAILABLE" }
  }]
}
  • Lỗi ở một trường không làm hỏng cả response: trường đó thành null, phần còn lại vẫn trả về. Nếu trường là non-null thì null lan lên cha gần nhất cho phép null.
  • Nhiều server trả HTTP 200 kể cả khi có lỗi nghiệp vụ. Spec GraphQL over HTTP đề xuất dùng content type application/graphql-response+json và status 4xx khi request không hợp lệ.
  • Cache khó hơn REST vì mọi request đều là POST tới một URL. Cách xử lý: client cache chuẩn hóa theo id (Apollo, urql), persisted query gửi hash thay cho cả query và cho phép dùng GET để CDN cache.

07Bảo mật & hiệu năng

  • Client tự viết query nên có thể gửi query lồng rất sâu hoặc rất tốn kém. Cần giới hạn độ sâu, độ phức tạp (tính điểm theo số trường và kích thước list) và timeout.
  • Rate limit theo chi phí query, không chỉ theo số request.
  • Persisted query dạng allowlist: production chỉ chấp nhận các query đã đăng ký trước. Rất hợp với ứng dụng nội bộ.
  • Cân nhắc tắt introspection ở API công khai nếu không cần, và tắt gợi ý tên trường trong thông báo lỗi.
  • Phân quyền ở tầng resolver hoặc business logic, không chỉ ở endpoint, vì một endpoint phục vụ mọi thứ.
  • Upload file không có trong spec chuẩn; thường upload qua REST hoặc presigned URL rồi gửi URL vào mutation.

08Federation: nhiều service, một schema

Khi có nhiều team, mỗi service sở hữu một phần schema (subgraph). Một router/gateway ghép chúng thành supergraph và tự chia query thành các lời gọi tới từng subgraph.

Cách làmĐặc điểm
Apollo FederationPhổ biến nhất. Subgraph đánh dấu entity bằng @key, router lo việc ghép.
Schema stitchingCách cũ hơn, ghép schema thủ công ở gateway.
BFF (Backend for Frontend)Một server GraphQL cho từng loại client, phía sau gọi REST hoặc gRPC.
