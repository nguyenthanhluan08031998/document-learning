Sổ tay gRPC: gọi hàm từ xa qua HTTP/2

gRPC là framework RPC mã nguồn mở do Google khởi xướng, nay thuộc CNCF. Bạn mô tả service trong file .proto, công cụ sinh code client và server cho nhiều ngôn ngữ, rồi gọi service ở máy khác như gọi một hàm bình thường.

02Luồng một lời gọi (unary)

  • Request là một HTTP/2 stream: frame HEADERS chứa :path /shop.OrderService/GetOrder và content-type: application/grpc, tiếp theo là frame DATA chứa message đã serialize (có 5 byte tiền tố độ dài).
  • Kết quả nằm ở trailers cuối stream: grpc-status và grpc-message. HTTP status gần như luôn là 200.
  • Interceptor (giống middleware) dùng cho xác thực, log, metrics, tracing, retry ở cả hai phía.

03Protocol Buffers

syntax = "proto3";
package shop.v1;

service OrderService {
  rpc GetOrder (GetOrderRequest) returns (Order);                    // unary
  rpc WatchOrder (GetOrderRequest) returns (stream OrderEvent);      // server streaming
  rpc UploadItems (stream Item) returns (UploadSummary);             // client streaming
  rpc Chat (stream ChatMessage) returns (stream ChatMessage);        // bidirectional
}

message GetOrderRequest { string id = 1; }

message Order {
  string id = 1;          // field number, not a value
  int64 total = 2;
  Status status = 3;
  repeated Item items = 4;
  reserved 5;             // field 5 was removed; never reuse it
}

enum Status { STATUS_UNSPECIFIED = 0; PAID = 1; SHIPPED = 2; }
  • Trên dây chỉ gửi số thứ tự trường và giá trị, không gửi tên, nên rất gọn. Số trường 1–15 chỉ tốn 1 byte cho phần nhãn, dành cho các trường hay dùng.
  • Tương thích ngược: được thêm trường mới; không đổi số hay kiểu của trường cũ; xóa trường thì đưa số vào reserved.
  • Trường không gửi sẽ nhận giá trị mặc định (0, chuỗi rỗng). Cần phân biệt “không có” với “bằng 0” thì dùng optional hoặc wrapper type.
  • Ngoài proto3, Protobuf có thêm cú pháp Editions để thay dần proto2/proto3 bằng các tùy chọn tính năng.

05Deadline, metadata & status code

  • Deadline: client đặt thời điểm hết hạn cho mỗi lời gọi. Hết hạn thì cả client và server nhận tín hiệu hủy, và deadline được truyền tiếp sang các service gọi sau. Luôn đặt deadline; mặc định là không giới hạn.
  • Metadata: cặp key–value đi kèm lời gọi, giống HTTP header, dùng cho token, trace id. Key kết thúc bằng -bin chứa dữ liệu nhị phân.
  • Retry khai báo qua service config, chỉ nên retry các mã an toàn như UNAVAILABLE.

06Load balancing: cái bẫy hay gặp

gRPC giữ một connection HTTP/2 lâu dài và dồn mọi lời gọi vào đó. Load balancer tầng 4 (TCP) chỉ chia connection, nên toàn bộ request của một client rơi vào cùng một server dù bạn có 10 server.

L7 proxy

Envoy, NGINX, Linkerd, Istio hiểu HTTP/2 và chia theo từng request. Dễ triển khai, thêm một bước nhảy mạng.

Client-side LB

Client tự biết danh sách server (DNS, xDS) và chia tải, ví dụ chính sách round_robin. Nhanh nhất, nhưng logic nằm ở client.

Trên Kubernetes, một Service ClusterIP thông thường là L4, nên cần headless service với client-side LB, hoặc service mesh.

07Trình duyệt & công cụ

  • Trình duyệt không điều khiển được HTTP/2 frame và trailers, nên không gọi gRPC trực tiếp được. Dùng gRPC-Web qua proxy (Envoy), hoặc giao thức Connect chạy được cả HTTP/1.1 lẫn JSON.
  • Transcoding: grpc-gateway hoặc Envoy sinh REST/JSON API từ cùng file .proto (dùng annotation google.api.http) cho client bên ngoài.
  • Server reflection cho phép công cụ hỏi danh sách service; grpcurl gọi thử như curl.
  • Health checking protocol chuẩn (grpc.health.v1.Health) để load balancer và Kubernetes kiểm tra server.
  • buf giúp lint, phát hiện thay đổi phá tương thích (buf breaking) và quản lý file .proto.
