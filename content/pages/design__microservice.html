Pattern cho microservice

Khi hệ thống tách thành nhiều service giao tiếp qua mạng (REST, gRPC, Kafka, RabbitMQ, NATS), xuất hiện những vấn đề mới: giao dịch xuyên service, gửi sự kiện tin cậy, lỗi lan dây chuyền. Đây là các lời giải phổ biến.

01Database per Service Mỗi service một database

Vấn đềNhiều service dùng chung một database thì đổi schema một bảng là ảnh hưởng tất cả, và không triển khai độc lập được.
Ý tưởngMỗi service sở hữu dữ liệu riêng, service khác chỉ truy cập qua API hoặc sự kiện.
Khi nào dùngGần như mặc định khi tách microservice.
Lưu ýMất JOIN và transaction xuyên service; cần Saga cho giao dịch và CQRS hoặc API Composition cho truy vấn gộp.

02Saga Giao dịch phân tán

Vấn đềĐặt hàng cần trừ kho, trừ tiền, tạo vận đơn ở ba service với ba database. Không có transaction chung để rollback.
Ý tưởngChia thành chuỗi transaction cục bộ. Bước nào thất bại thì chạy các hành động bù trừ (compensation) theo thứ tự ngược lại.
type Step = { name: string; run: () => Promise<void>; compensate: () => Promise<void> };

async function runSaga(steps: Step[]) {
  const done: Step[] = [];
  try {
    for (const s of steps) { await s.run(); done.push(s); }
  } catch (err) {
    // Undo completed steps in reverse order
    for (const s of done.reverse()) await s.compensate();
    throw err;
  }
}

await runSaga([
  { name: "reserve stock", run: () => inventory.reserve(order), compensate: () => inventory.release(order) },
  { name: "charge",        run: () => payment.charge(order),    compensate: () => payment.refund(order) },
  { name: "ship",          run: () => shipping.create(order),   compensate: () => shipping.cancel(order) },
]);
Khi nào dùngMọi nghiệp vụ trải qua nhiều service cần nhất quán cuối cùng.
Lưu ýCode mẫu là orchestration trong bộ nhớ; thực tế phải lưu trạng thái saga vào DB để sống sót khi service restart, và mỗi bước phải idempotent.

03Orchestration vs Choreography Nhạc trưởng hay tự nhảy

Vấn đềMột quy trình chạy qua nhiều service (giữ hàng, trừ tiền, giao hàng). Ai quyết định bước tiếp theo, và khi một bước lỗi thì ai lo bù trừ?
Ý tưởngOrchestration: một orchestrator biết cả quy trình và ra lệnh cho từng service. Choreography: không có trung tâm, mỗi service nghe sự kiện của bước trước rồi tự làm phần mình và phát sự kiện mới.
// Choreography: each service only reacts to events (Kafka / NATS / RabbitMQ)
inventory.on("OrderCreated", async e => {
  await reserve(e.items);
  await publish("StockReserved", { orderId: e.orderId, items: e.items });
});

payment.on("StockReserved", async e => {
  try {
    await charge(e.orderId);
    await publish("PaymentDone", { orderId: e.orderId });
  } catch {
    await publish("PaymentFailed", { orderId: e.orderId, items: e.items });
  }
});

// Compensation is also just another listener
inventory.on("PaymentFailed", e => release(e.items));
orders.on("PaymentFailed", e => markCancelled(e.orderId));
OrchestrationChoreography
Ai biết cả quy trìnhOrchestratorKhông ai, logic nằm rải rác
Giao tiếpLệnh (gRPC, REST, command message)Sự kiện qua event bus
Liên kếtOrchestrator phụ thuộc mọi serviceLỏng, chỉ phụ thuộc định dạng sự kiện
Theo dõi, debugDễ, trạng thái nằm một chỗKhó, cần distributed tracing
Bù trừ khi lỗiTập trung, đúng thứ tự ngượcMỗi service tự nghe sự kiện lỗi
Thêm bước mớiSửa orchestratorThêm listener, không sửa ai
Rủi roOrchestrator thành “god service”Mạng sự kiện rối, vòng lặp khó thấy
Công cụTemporal, Camunda/Zeebe, AWS Step FunctionsKafka, RabbitMQ, NATS
Khi nào dùngOrchestration cho quy trình dài, nhiều nhánh, cần biết đơn đang ở đâu (đặt hàng, duyệt vay). Choreography cho chuỗi ngắn hoặc khi một sự kiện có nhiều bên cùng quan tâm (OrderPaid → email, thống kê, tích điểm).
Lưu ýThực tế hay kết hợp: orchestration cho luồng chính cần kiểm soát, phát sự kiện cho các việc phụ. Dù cách nào, mỗi bước đều phải idempotent và gửi sự kiện qua Outbox.

04Transactional Outbox Hộp thư đi

Vấn đềLưu đơn vào DB rồi publish sự kiện lên Kafka: nếu DB thành công mà publish lỗi (hoặc ngược lại) thì hai bên lệch nhau. Đây là vấn đề dual write.
Ý tưởngGhi sự kiện vào bảng outbox trong cùng transaction với dữ liệu nghiệp vụ. Một tiến trình riêng đọc bảng outbox và publish lên broker.
// 1. Business write and event write share one DB transaction
await db.transaction(async tx => {
  await tx.insert("orders", order);
  await tx.insert("outbox", {
    id: crypto.randomUUID(),
    topic: "orders.created",
    payload: JSON.stringify(order),
    created_at: new Date(),
  });
});

// 2. A relay process publishes pending rows, then marks them as sent
async function relay() {
  const rows = await db.query("SELECT * FROM outbox WHERE sent_at IS NULL ORDER BY created_at LIMIT 100");
  for (const r of rows) {
    await producer.send({ topic: r.topic, messages: [{ key: r.id, value: r.payload }] });
    await db.query("UPDATE outbox SET sent_at = now() WHERE id = $1", [r.id]);
  }
}
setInterval(relay, 1000);
Khi nào dùngBất cứ khi nào vừa cập nhật DB vừa phải gửi sự kiện.
Lưu ýRelay có thể gửi trùng nếu chết giữa publish và update, nên phía nhận cần Idempotent Consumer. Thay cho polling có thể dùng CDC (Debezium đọc WAL của DB).

05Idempotent Consumer Consumer chịu được trùng lặp

Vấn đềKafka, RabbitMQ, JetStream đều có thể giao một message nhiều lần (at-least-once). Xử lý hai lần thì trừ tiền hai lần.
Ý tưởngGhi lại id của message đã xử lý, trong cùng transaction với thay đổi nghiệp vụ; gặp lại id cũ thì bỏ qua.
async function handle(msg: { id: string; orderId: string; amount: number }) {
  await db.transaction(async tx => {
    // Unique constraint on processed_messages.id rejects duplicates
    const inserted = await tx.query(
      "INSERT INTO processed_messages(id) VALUES ($1) ON CONFLICT DO NOTHING RETURNING id",
      [msg.id],
    );
    if (inserted.rowCount === 0) return; // already handled

    await tx.query("UPDATE wallets SET balance = balance - $1 WHERE order_id = $2",
      [msg.amount, msg.orderId]);
  });
}
Khi nào dùngMọi consumer có tác dụng phụ (ghi DB, trừ tiền, gửi email).
Lưu ýBảng id đã xử lý cần được dọn định kỳ. Thao tác tự nhiên idempotent (ghi đè giá trị) thì không cần bảng này.

06CQRS Tách ghi và đọc

Vấn đềMô hình dữ liệu tối ưu cho ghi (chuẩn hóa, nhiều ràng buộc) lại chậm cho các màn hình đọc cần JOIN nhiều bảng hoặc nhiều service.
Ý tưởngTách command (ghi) và query (đọc) thành hai mô hình. Phía ghi phát sự kiện; phía đọc nghe sự kiện và cập nhật một view tối ưu sẵn cho truy vấn.
// Write side: validates and emits events
async function placeOrder(cmd: PlaceOrder) {
  const order = Order.create(cmd);          // business rules
  await orderRepo.save(order);
  await outbox.add("orders.placed", order.toEvent());
}

// Read side: a projection kept up to date from events
consumer.on("orders.placed", async e => {
  await readDb.collection("order_summaries").updateOne(
    { customerId: e.customerId },
    { $inc: { orderCount: 1, totalSpent: e.total }, $set: { lastOrderAt: e.at } },
    { upsert: true },
  );
});

// Queries hit the denormalized view directly
const summary = await readDb.collection("order_summaries").findOne({ customerId: "7" });
Khi nào dùngTải đọc và ghi chênh lệch lớn, màn hình đọc phức tạp, kết hợp với Event Sourcing.
Lưu ýView đọc trễ hơn phía ghi một chút (eventual consistency). Đừng áp dụng cho CRUD đơn giản.

07Event Sourcing Lưu chuỗi sự kiện

Vấn đềChỉ lưu trạng thái hiện tại thì mất lịch sử: không biết số dư thay đổi thế nào, khó kiểm toán và khó dựng lại.
Ý tưởngLưu mọi sự kiện đã xảy ra theo thứ tự (chỉ thêm, không sửa). Trạng thái hiện tại là kết quả “gộp” các sự kiện.
type AccountEvent =
  | { type: "Opened"; owner: string }
  | { type: "Deposited"; amount: number }
  | { type: "Withdrawn"; amount: number };

function rebuild(events: AccountEvent[]) {
  // Fold events into current state
  return events.reduce((acc, e) => {
    switch (e.type) {
      case "Opened": return { owner: e.owner, balance: 0 };
      case "Deposited": return { ...acc, balance: acc.balance + e.amount };
      case "Withdrawn": return { ...acc, balance: acc.balance - e.amount };
    }
  }, { owner: "", balance: 0 });
}

const history: AccountEvent[] = await eventStore.load("account-7");
const state = rebuild(history); // { owner: "An", balance: 1_200_000 }
Khi nào dùngTài chính, kiểm toán, hệ thống cần “du hành thời gian”. Kafka với retention vô hạn hoặc JetStream thường làm event store.
Lưu ýPhức tạp: cần snapshot khi chuỗi dài, đổi cấu trúc sự kiện cũ rất khó, truy vấn phải qua CQRS.

08Circuit Breaker Cầu dao

Vấn đềService B chậm hoặc chết; service A vẫn gọi liên tục, mỗi lời gọi chờ timeout, thread cạn dần và A chết theo. Lỗi lan dây chuyền.
Ý tưởngĐếm lỗi; vượt ngưỡng thì “ngắt cầu dao” và trả lỗi ngay không gọi B nữa. Sau một lúc cho thử vài lời gọi; thành công thì đóng lại.
type State = "closed" | "open" | "half-open";

class CircuitBreaker {
  private state: State = "closed";
  private failures = 0;
  private openedAt = 0;
  constructor(private threshold = 5, private resetMs = 10_000) {}

  async call<T>(fn: () => Promise<T>): Promise<T> {
    if (this.state === "open") {
      if (Date.now() - this.openedAt < this.resetMs) throw new Error("Circuit open");
      this.state = "half-open"; // allow a trial call
    }
    try {
      const result = await fn();
      this.state = "closed";
      this.failures = 0;
      return result;
    } catch (err) {
      this.failures++;
      if (this.state === "half-open" || this.failures >= this.threshold) {
        this.state = "open";
        this.openedAt = Date.now();
      }
      throw err;
    }
  }
}

const breaker = new CircuitBreaker();
const price = await breaker.call(() => pricingClient.getPrice("SKU-1"));
Khi nào dùngMọi lời gọi đồng bộ sang service khác hoặc API bên ngoài.
Lưu ýKết hợp với timeout và fallback (giá trị cache, thông báo thân thiện). Thư viện có sẵn: opossum (Node.js); service mesh cũng làm được.

09Retry + Backoff + Jitter Thử lại có giãn cách

Vấn đềLỗi tạm thời (mạng chập chờn, 503) có thể tự hết, nhưng retry ngay lập tức với cùng nhịp làm server đang yếu càng quá tải.
Ý tưởngThử lại với thời gian chờ tăng dần theo cấp số nhân, cộng thêm ngẫu nhiên (jitter) để các client không retry cùng lúc.
async function retry<T>(fn: () => Promise<T>, attempts = 5, baseMs = 200): Promise<T> {
  for (let i = 0; ; i++) {
    try {
      return await fn();
    } catch (err) {
      if (i >= attempts - 1 || !isTransient(err)) throw err;
      // Full jitter: random delay between 0 and base * 2^i
      const delay = Math.random() * baseMs * 2 ** i;
      await new Promise(r => setTimeout(r, delay));
    }
  }
}

const isTransient = (e: any) => [502, 503, 504].includes(e.status) || e.code === "ECONNRESET";
Khi nào dùngLỗi tạm thời ở mạng, broker, database.
Lưu ýChỉ retry thao tác idempotent (hoặc có Idempotency-Key). Retry nhiều tầng chồng nhau sẽ nhân số request lên rất nhanh.

10Bulkhead Vách ngăn

Vấn đềMột dependency chậm chiếm hết connection pool hoặc worker, kéo theo cả những tính năng không liên quan.
Ý tưởngChia tài nguyên thành các khoang riêng cho từng dependency, như vách ngăn chống chìm tàu.
// Limit concurrent calls per dependency
function limiter(max: number) {
  let active = 0;
  const queue: (() => void)[] = [];
  return async <T>(fn: () => Promise<T>): Promise<T> => {
    if (active >= max) await new Promise<void>(r => queue.push(r));
    active++;
    try { return await fn(); }
    finally { active--; queue.shift()?.(); }
  };
}

const forPayment = limiter(20);
const forRecommendation = limiter(5); // slow, non-critical dependency gets a small share

await forRecommendation(() => recoClient.get(userId));
Khi nào dùngService gọi nhiều dependency có mức quan trọng khác nhau.
Lưu ýChọn kích thước khoang dựa trên đo đạc; quá nhỏ thì tự bóp nghẹt mình.

11Strangler Fig Thay dần hệ thống cũ

Vấn đềViết lại toàn bộ hệ thống monolith một lần quá rủi ro.
Ý tưởngĐặt một proxy/gateway phía trước, chuyển dần từng route sang service mới; route chưa chuyển vẫn đi vào hệ thống cũ cho tới khi cũ không còn gì.
// API gateway routing table during migration
const routes: { prefix: string; target: string }[] = [
  { prefix: "/api/orders",   target: "http://order-service" },   // migrated
  { prefix: "/api/payments", target: "http://payment-service" }, // migrated
  { prefix: "/",             target: "http://legacy-monolith" }, // everything else
];

const pickTarget = (path: string) => routes.find(r => path.startsWith(r.prefix))!.target;
Khi nào dùngHiện đại hóa hệ thống cũ, tách monolith thành microservice.
Lưu ýDữ liệu dùng chung giữa cũ và mới là phần khó nhất; cần kế hoạch đồng bộ dữ liệu.

12Sidecar / Service Mesh Xe thùng bên cạnh

Vấn đềService nào cũng cần TLS, retry, metrics, tracing; viết lại cho từng ngôn ngữ thì tốn công và không đồng nhất.
Ý tưởngChạy một tiến trình phụ (sidecar, thường là Envoy) bên cạnh mỗi service để lo phần hạ tầng mạng. Tập hợp các sidecar gọi là service mesh (Istio, Linkerd).
Khi nào dùngNhiều service, nhiều ngôn ngữ, cần mTLS và quan sát đồng nhất.
Lưu ýThêm độ trễ và độ phức tạp vận hành; hệ thống nhỏ chưa cần.
