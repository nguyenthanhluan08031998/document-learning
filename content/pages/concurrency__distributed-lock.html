Distributed lock: khóa xuyên nhiều máy

Khi ứng dụng chạy nhiều instance, lock trong bộ nhớ của một instance không ngăn được instance khác. Distributed lock đặt “chìa khóa” ở một hệ thống mà mọi instance cùng thấy. Khó hơn lock thường nhiều, vì mạng có thể chậm, tiến trình có thể dừng giữa chừng và đồng hồ có thể lệch.

01Lock trong một tiến trình: mutex & semaphore

Node.js chạy một luồng nhưng các hàm async vẫn xen kẽ nhau tại mỗi await. Muốn một đoạn code async chỉ chạy một lần tại một thời điểm trong cùng tiến trình, dùng mutex (ví dụ thư viện async-mutex).

import { Mutex, Semaphore } from "async-mutex";

// Mutex: only one refresh at a time inside this process
const tokenMutex = new Mutex();
let cachedToken: string | undefined;

async function getAccessToken() {
  return tokenMutex.runExclusive(async () => {
    if (!cachedToken) cachedToken = await fetchNewToken(); // other callers wait, then reuse
    return cachedToken;
  });
}

// Semaphore: at most 5 concurrent calls to a slow API (see Bulkhead pattern)
const apiSlots = new Semaphore(5);
await apiSlots.runExclusive(() => callSlowApi());
Mutex trong bộ nhớ chỉ có tác dụng trong một instance. Chạy 3 pod thì có 3 mutex độc lập. Đó là lúc cần distributed lock, hoặc tốt hơn, một cơ chế ở database.

02Khi nào cần distributed lock

  • Cron job chạy trên nhiều instance: chỉ một instance được gửi báo cáo cuối ngày.
  • Gọi hệ thống ngoài không có idempotency: chỉ một tiến trình được làm mới token OAuth dùng chung.
  • Tài nguyên không nằm trong một database: file trên S3, nhiều hệ thống cùng chạm vào.
  • Bầu leader: một instance làm việc nền, các instance khác dự phòng.
Nếu dữ liệu nằm trong một database, hãy ưu tiên atomic update, FOR UPDATE hoặc optimistic lock ở tab trước. Chúng nằm trong transaction nên an toàn hơn distributed lock nhiều.

03Redis lock: cách phổ biến nhất

  1. Lấy khóa
    SET lock:report <token> NX PX 30000: chỉ đặt nếu chưa có (NX), tự hết hạn sau 30 giây (PX) để không kẹt mãi nếu tiến trình chết.
  2. Làm việc
    Phải xong trước khi khóa hết hạn, hoặc gia hạn định kỳ.
  3. Nhả khóa đúng chủ
    Chỉ xóa nếu giá trị vẫn là token của mình, bằng một script Lua để kiểm tra và xóa là một thao tác atomic.
import Redis from "ioredis";
import { randomUUID } from "node:crypto";

const redis = new Redis(process.env.REDIS_URL!);

const RELEASE_SCRIPT = `
  if redis.call("get", KEYS[1]) == ARGV[1] then
    return redis.call("del", KEYS[1])
  end
  return 0
`;

async function withLock<T>(key: string, ttlMs: number, fn: () => Promise<T>): Promise<T | null> {
  const token = randomUUID();                       // identifies the owner
  const ok = await redis.set(key, token, "PX", ttlMs, "NX");
  if (ok !== "OK") return null;                     // someone else holds it: non-blocking
  try {
    return await fn();
  } finally {
    // Never delete a lock that expired and now belongs to someone else
    await redis.eval(RELEASE_SCRIPT, 1, key, token);
  }
}

// Only one instance sends the daily report
await withLock("lock:daily-report", 60_000, () => sendDailyReport());
Vì sao cần tokenNếu xóa bằng DEL thường: A giữ khóa quá TTL, khóa hết hạn, B lấy được; A làm xong gọi DEL và xóa mất khóa của B.
Giới hạnMột Redis đơn: Redis chết hoặc failover sang replica chưa kịp đồng bộ thì khóa có thể mất, hai bên cùng giữ.

04Lease hết hạn & fencing token

Mọi distributed lock có TTL đều là lease (thuê có hạn). Vấn đề: tiến trình có thể bị dừng (GC pause, máy treo, mạng chậm) lâu hơn TTL mà không biết. Khi tỉnh lại, nó tưởng mình vẫn giữ khóa và ghi đè lên việc của người khác.

// Each successful acquire returns a strictly increasing number
const fencingToken = await redis.incr("lock:invoice:fence");

// The storage accepts a write only if the token is newer than the last one it saw
const res = await db.query(
  "UPDATE invoices SET pdf_url = $1, fence = $2 WHERE id = $3 AND fence < $2",
  [url, fencingToken, invoiceId],
);
if (res.rowCount === 0) throw new Error("Stale lock holder, write rejected");

Lock giúp giảm trùng lặp; fencing token ở phía lưu trữ mới đảm bảo đúng. etcd (revision) và ZooKeeper (zxid) cung cấp sẵn số tăng dần dùng làm fencing token.

05Redlock

Thuật toán của tác giả Redis để không phụ thuộc một node: dùng N node Redis độc lập (thường 5), lấy khóa trên từng node, coi là thành công nếu được đa số (ít nhất 3) trong thời gian ngắn hơn TTL. Thư viện Node.js: redlock.

Ủng hộ

Chịu được một số node Redis chết; đủ tốt khi lock chỉ để tránh làm trùng việc (hiệu năng), không phải để đảm bảo đúng tuyệt đối.

Phê bình (Martin Kleppmann, 2016)

Dựa vào giả định về thời gian và đồng hồ; không có fencing token nên vẫn hỏng khi tiến trình bị dừng lâu. Cần đúng tuyệt đối thì dùng hệ thống đồng thuận (etcd, ZooKeeper) kèm fencing.

Cách nghĩ thực dụng: lock để tiết kiệm công (tránh hai máy cùng tính một báo cáo) thì Redis là đủ; lock để giữ đúng dữ liệu (tiền, tồn kho) thì đưa kiểm tra vào database hoặc dùng fencing.

06etcd, ZooKeeper, PostgreSQL advisory lock

Công cụCách hoạt độngĐiểm mạnh
etcdKey gắn với lease, client gửi keep-alive; hết keep-alive thì key tự xóa. Revision tăng dần dùng làm fencing token.Đồng thuận Raft, nhất quán mạnh; Kubernetes dùng cho leader election.
ZooKeeperTạo znode ephemeral sequential; ai có số nhỏ nhất giữ khóa, người khác theo dõi node đứng trước mình.Đã được kiểm chứng lâu (Kafka bản cũ, Hadoop); công thức lock có sẵn trong Curator.
PostgreSQL advisory lockKhóa theo một số nguyên do ứng dụng tự đặt nghĩa: pg_try_advisory_xact_lock(hashtext('daily-report')).Không cần thêm hạ tầng nếu đã có PostgreSQL; bản _xact_ tự nhả khi transaction kết thúc.
 
// PostgreSQL advisory lock: one runner for a scheduled job across all instances
const client = await pool.connect();
try {
  await client.query("BEGIN");
  const { rows } = await client.query(
    "SELECT pg_try_advisory_xact_lock(hashtext($1)) AS ok", ["daily-report"],
  );
  if (rows[0].ok) await sendDailyReport(client);   // others skip immediately
  await client.query("COMMIT");                    // lock released with the transaction
} finally {
  client.release();
}
Advisory lock dạng session (pg_advisory_lock) gắn với connection. Qua PgBouncer ở chế độ transaction pooling, connection bị dùng chung nên khóa có thể không như mong đợi; dùng bản _xact_ trong transaction.

07Quy tắc dùng distributed lock an toàn

  1. Luôn có TTL
    Tiến trình chết thì khóa phải tự nhả.
  2. Nhả đúng chủ
    So token trước khi xóa, bằng thao tác atomic.
  3. Gia hạn cho việc dài
    Gia hạn định kỳ (watchdog), dừng việc nếu gia hạn thất bại.
  4. Chờ có giới hạn
    Thử lại vài lần với backoff, không chờ vô hạn.
  5. Dữ liệu quan trọng thì thêm fencing hoặc kiểm tra ở database
    Đừng chỉ tin vào việc “mình đang giữ khóa”.
  6. Hỏi lại xem có cần lock không
    Unique constraint, idempotency key hoặc một consumer cho mỗi key thường đơn giản và chắc chắn hơn.
