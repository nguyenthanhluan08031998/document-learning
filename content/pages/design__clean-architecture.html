Clean Architecture: nghiệp vụ ở giữa, framework ở rìa

Kiến trúc do Robert C. Martin (Uncle Bob) tổng hợp. Ý chính: code nghiệp vụ không được biết gì về database, web framework hay message broker. Nhờ vậy đổi Postgres sang MongoDB, Express sang NestJS, REST sang gRPC mà không phải sửa logic, và test nghiệp vụ không cần khởi động gì cả.

02Dependency Rule

Phụ thuộc trong code chỉ được hướng vào trong. Vòng trong không import, không nhắc tên bất cứ thứ gì ở vòng ngoài: không import express, không kiểu dữ liệu của Prisma, không annotation của ORM.

Nhưng lúc chạy, use case vẫn phải gọi ra database ở vòng ngoài. Cách giải là Dependency Inversion: use case định nghĩa interface (port), vòng ngoài hiện thực interface đó (adapter), và một chỗ duy nhất gọi là composition root nối chúng lại.

Dữ liệu qua ranh giới nên là object đơn giản (DTO), không truyền nguyên request của Express hay row của ORM vào use case.

03Luồng một request

  1. Controller (adapter)
    Nhận HTTP request, đọc và kiểm tra định dạng, chuyển thành input DTO.
  2. Use case
    Chạy quy trình: tải entity qua port, gọi quy tắc của entity, lưu lại qua port, phát sự kiện.
  3. Entity
    Tự bảo vệ quy tắc nghiệp vụ, ví dụ không cho tổng tiền âm.
  4. Repository adapter
    Hiện thực port bằng Postgres; chuyển entity sang row và ngược lại.
  5. Trả kết quả
    Use case trả output DTO; controller (hoặc presenter) đổi thành HTTP response, status code.

04Code mẫu TypeScript

Entity: nghiệp vụ thuần

// domain/order.ts — no imports from frameworks
export class Order {
  private constructor(
    readonly id: string,
    readonly customerId: string,
    private items: { sku: string; price: number; qty: number }[],
    private status: "pending" | "paid" = "pending",
  ) {}

  static create(id: string, customerId: string) { return new Order(id, customerId, []); }

  addItem(sku: string, price: number, qty: number) {
    if (this.status !== "pending") throw new Error("Order already paid");
    if (qty <= 0) throw new Error("Quantity must be positive");
    this.items.push({ sku, price, qty });
  }

  total() { return this.items.reduce((s, i) => s + i.price * i.qty, 0); }
  markPaid() { this.status = "paid"; }
}

Use case và port

// application/ports.ts — interfaces owned by the inner layer
export interface OrderRepository {
  save(order: Order): Promise<void>;
  findById(id: string): Promise<Order | null>;
}
export interface EventPublisher { publish(topic: string, payload: object): Promise<void>; }
export interface IdGenerator { next(): string; }

// application/place-order.ts
export type PlaceOrderInput = { customerId: string; items: { sku: string; price: number; qty: number }[] };
export type PlaceOrderOutput = { orderId: string; total: number };

export class PlaceOrder {
  constructor(
    private orders: OrderRepository,
    private events: EventPublisher,
    private ids: IdGenerator,
  ) {}

  async execute(input: PlaceOrderInput): Promise<PlaceOrderOutput> {
    const order = Order.create(this.ids.next(), input.customerId);
    for (const i of input.items) order.addItem(i.sku, i.price, i.qty);
    await this.orders.save(order);
    await this.events.publish("orders.placed", { id: order.id, total: order.total() });
    return { orderId: order.id, total: order.total() };
  }
}

Adapter: hiện thực port

// infrastructure/postgres-order-repository.ts
import { Pool } from "pg";

export class PostgresOrderRepository implements OrderRepository {
  constructor(private pool: Pool) {}
  async save(order: Order) {
    await this.pool.query(
      "INSERT INTO orders(id, customer_id, total) VALUES ($1, $2, $3) ON CONFLICT (id) DO UPDATE SET total = $3",
      [order.id, order.customerId, order.total()],
    );
  }
  async findById(id: string) { /* map row -> Order */ return null; }
}

// interface/http/order-controller.ts
import type { Request, Response } from "express";

export const placeOrderHandler = (useCase: PlaceOrder) => async (req: Request, res: Response) => {
  try {
    const out = await useCase.execute({ customerId: req.body.customerId, items: req.body.items });
    res.status(201).location(`/orders/${out.orderId}`).json(out);
  } catch (e) {
    res.status(422).json({ title: "Invalid order", detail: (e as Error).message });
  }
};

Test use case không cần database

// In-memory fakes implement the same ports
class InMemoryOrders implements OrderRepository {
  data = new Map<string, Order>();
  async save(o: Order) { this.data.set(o.id, o); }
  async findById(id: string) { return this.data.get(id) ?? null; }
}

test("places an order and publishes an event", async () => {
  const orders = new InMemoryOrders();
  const published: object[] = [];
  const useCase = new PlaceOrder(orders, { publish: async (_t, p) => { published.push(p); } }, { next: () => "o-1" });

  const out = await useCase.execute({ customerId: "c-7", items: [{ sku: "A", price: 50_000, qty: 2 }] });

  expect(out).toEqual({ orderId: "o-1", total: 100_000 });
  expect(published).toHaveLength(1);
});

05Cấu trúc thư mục gợi ý

src/
  domain/              # Entities, value objects, domain errors — no dependencies
    order.ts
  application/         # Use cases + ports (interfaces) — depends on domain only
    ports.ts
    place-order.ts
    cancel-order.ts
  infrastructure/      # Adapters to the outside world — implements ports
    postgres-order-repository.ts
    kafka-event-publisher.ts
  interface/           # Delivery mechanisms
    http/order-controller.ts
    grpc/order-service.ts
  main.ts              # Composition root

Có thể dùng công cụ như dependency-cruiser hoặc luật ESLint để chặn domain/ import từ infrastructure/, biến Dependency Rule thành kiểm tra tự động.

Với hệ thống lớn, nhiều đội chia thư mục theo tính năng trước (orders/, payments/), rồi mới chia tầng bên trong mỗi tính năng.

06Hexagonal & Onion: cùng một gia đình

Kiến trúcTác giảCách gọi
Hexagonal (Ports & Adapters)Alistair Cockburn, 2005Lõi ứng dụng ở giữa, mỗi cạnh là một port; driving adapter (HTTP, CLI, consumer) gọi vào, driven adapter (DB, broker) được gọi ra.
OnionJeffrey Palermo, 2008Domain model ở tâm, domain services, application services, rồi hạ tầng ở lớp ngoài.
CleanRobert C. Martin, 2012Gộp các ý trên thành bốn vòng và Dependency Rule.

Cả ba có chung một ý: nghiệp vụ ở trung tâm, phụ thuộc hướng vào trong, hạ tầng là chi tiết có thể thay. Khác biệt chủ yếu ở tên gọi và số lớp.

Liên hệ với các phần khác của sổ tay: KafkaJS producer, Express route, gRPC server, RabbitMQ consumer đều là adapter ở vòng ngoài. Use case không cần biết sự kiện đi qua Kafka hay NATS, chỉ biết port EventPublisher.

07Khi nào dùng, lỗi hay gặp

Nên dùng khi

  • Nghiệp vụ phức tạp, sống lâu, nhiều quy tắc.
  • Cần test nghiệp vụ nhanh, độc lập hạ tầng.
  • Có khả năng đổi database, framework, hoặc thêm kênh giao tiếp (REST, gRPC, consumer).

Chưa cần khi

  • CRUD đơn giản, ít logic: ba lớp interface cho mỗi bảng chỉ làm chậm.
  • Prototype, script, service rất nhỏ.
  • Đội chưa quen; áp dụng nửa vời còn tệ hơn không áp dụng.

Lỗi hay gặp

  • Entity “thiếu máu”: chỉ có getter/setter, mọi quy tắc nằm trong use case hoặc controller.
  • Rò rỉ framework vào trong: entity mang decorator của ORM, use case nhận Request của Express.
  • Tạo interface cho mọi thứ, kể cả những thứ không bao giờ thay. Chỉ cần port ở chỗ chạm ra bên ngoài.
  • Use case gọi use case khác lồng nhau tạo thành mạng phụ thuộc; nên tách logic chung xuống entity hoặc domain service.
  • Ánh xạ dữ liệu quá nhiều lớp (DTO → command → entity → row → DTO) mà không lớp nào thêm giá trị.
