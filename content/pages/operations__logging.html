Logging: nhật ký của hệ thống

Log là bản ghi những gì ứng dụng đã làm. Khi có sự cố lúc 2 giờ sáng trên production, log tốt cho bạn biết chuyện gì xảy ra trong vài phút; log tệ (hoặc không có) bắt bạn đoán mò hàng giờ.

01Log để làm gì

Mục đíchVí dụ câu hỏi log trả lời được
Debug sự cốVì sao đơn 42 bị trừ tiền mà không tạo vận đơn?
Theo dõi hoạt độngHôm nay có bao nhiêu lần thanh toán thất bại, ở cổng nào?
Kiểm toán (audit)Ai đã đổi quyền của user 7, lúc nào?
Bảo mậtCó IP nào đăng nhập sai 100 lần trong một phút không?

02Log level

Mỗi dòng log có một mức độ. Production thường bật từ info trở lên; khi điều tra thì tạm hạ xuống debug.

LevelSố (pino)Khi nào dùngVí dụ
trace10Chi tiết từng bước, chỉ bật khi debug sâuGiá trị biến trong vòng lặp
debug20Thông tin cho developerCâu SQL đã chạy, cache hit/miss
info30Sự kiện nghiệp vụ bình thường, đáng ghi lạiĐơn hàng được tạo, server khởi động
warn40Bất thường nhưng hệ thống tự xử lý đượcRetry lần 2, gần hết quota, dùng giá trị mặc định
error50Một thao tác thất bại, cần người xemGọi cổng thanh toán lỗi sau mọi lần retry
fatal60Ứng dụng không thể chạy tiếpKhông kết nối được database lúc khởi động
Mẹo chọn level: nếu dòng log này xuất hiện lúc 2 giờ sáng, có cần đánh thức ai không? Có thì error. Cần xem trong giờ làm việc thì warn. Chỉ để tra cứu thì info. Lỗi do người dùng nhập sai (400, 404) thường là info hoặc warn, không phải error.

03Nên log gì

  • Ranh giới hệ thống: request đến và response đi (method, path, status, thời gian), lời gọi sang service khác, message nhận từ Kafka/RabbitMQ.
  • Sự kiện nghiệp vụ: tạo đơn, thanh toán thành công, đổi trạng thái.
  • Quyết định quan trọng: vì sao từ chối đơn, nhánh fallback nào được chọn.
  • Lỗi và retry: kèm nguyên nhân, số lần thử.
  • Khởi động và cấu hình: version, môi trường, cấu hình đã nạp (đã che bí mật).
  • Mỗi dòng có đủ ngữ cảnh: ai (userId), cái gì (orderId), request nào (requestId, traceId).

04Không được log gì

LoạiVí dụ
Bí mậtMật khẩu, token, API key, header Authorization, cookie phiên
Dữ liệu thanh toánSố thẻ, CVV
Dữ liệu cá nhânSố CCCD, số điện thoại, địa chỉ, email đầy đủ (che bớt: a***@gmail.com)
Body lớnCả request/response dài, file, ảnh base64

Log thường được lưu lâu và nhiều người đọc được, nên lộ bí mật qua log là lỗi bảo mật phổ biến. Dùng tính năng redact của thư viện để tự che các trường nhạy cảm, thay vì nhớ từng chỗ.

05Log lỗi đúng cách

// Bad: loses stack trace and context, and logs the same error at every layer
catch (e) {
  console.log("error: " + e);
  throw e;
}

// Good: wrap with context once, keep the original as "cause"
async function chargeOrder(orderId: string) {
  try {
    await paymentClient.charge(orderId);
  } catch (e) {
    throw new Error(`Charge failed for order ${orderId}`, { cause: e });
  }
}

// Log once, at the boundary that decides what to do with the error
app.use((err: Error, req: Request, res: Response, _next: NextFunction) => {
  req.log.error({ err, orderId: req.params.id }, "request failed");  // pino serializes stack + cause
  res.status(500).json({ title: "Internal error", requestId: req.id });
});
  • Log một lần, ở nơi quyết định xử lý lỗi. Log ở mọi tầng rồi ném tiếp sẽ tạo năm dòng cho cùng một lỗi.
  • Luôn giữ stack trace và nguyên nhân gốc (cause).
  • Trả cho người dùng requestId thay vì chi tiết lỗi, để họ báo lại và bạn tra log.

06Log đi đâu

  1. Ứng dụng ghi ra stdout
    Theo nguyên tắc 12-factor: ứng dụng không tự quản file log, chỉ in ra stdout dạng JSON.
  2. Bộ thu gom
    Docker, Kubernetes, Fluent Bit, Vector hoặc OpenTelemetry Collector đọc stdout của container và đẩy đi.
  3. Nơi lưu trữ và tìm kiếm
    Elasticsearch/OpenSearch + Kibana, Grafana Loki, Datadog, CloudWatch, Google Cloud Logging.
  4. Cảnh báo
    Đặt luật trên log: số dòng error tăng đột biến thì báo Slack hoặc gọi điện.
Nếu buộc phải ghi file, cần log rotation (logrotate, hoặc tính năng xoay vòng của thư viện) để không đầy ổ đĩa.
