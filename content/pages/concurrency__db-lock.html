Lock trong database

Ba cách chính để sửa dữ liệu an toàn trong một database: làm cho thao tác thành atomic, khóa trước (pessimistic), hoặc kiểm tra phiên bản lúc ghi (optimistic). Ví dụ dùng PostgreSQL và thư viện pg.

BEGIN
FOR UPDATE
UPDATE
COMMIT
version+1

01Atomic operation: cách đơn giản nhất

Nếu được, đừng đọc lên rồi mới ghi. Đẩy cả điều kiện lẫn phép tính vào một câu lệnh; database tự đảm bảo câu lệnh đó không bị chen ngang.

async function buy(productId: string) {
  // Check and decrement in one statement: no read-modify-write gap
  const res = await db.query(
    "UPDATE products SET stock = stock - 1 WHERE id = $1 AND stock > 0 RETURNING stock",
    [productId],
  );
  if (res.rowCount === 0) throw new Error("Sold out");
  return res.rows[0].stock;
}

// Same idea elsewhere
await redis.decr(`stock:${productId}`);                       // Redis atomic counter
await orders.updateOne({ _id: id }, { $inc: { views: 1 } });  // MongoDB $inc
Hợp vớiTăng giảm số đếm, trừ tồn kho, đổi trạng thái có điều kiện (WHERE status = 'pending').
Giới hạnChỉ dùng được khi logic gói gọn trong một câu lệnh trên một dòng hoặc một key. Logic phức tạp, nhiều bảng thì cần lock.

02Pessimistic lock: khóa trước, sửa sau

Giả định xung đột sẽ xảy ra, nên khóa dòng ngay khi đọc. Transaction khác muốn khóa cùng dòng phải chờ tới khi transaction đầu commit hoặc rollback.

async function transfer(fromId: string, toId: string, amount: number) {
  const client = await pool.connect();
  try {
    await client.query("BEGIN");
    // Lock both rows in a fixed order (by id) to avoid deadlocks
    const ids = [fromId, toId].sort();
    const { rows } = await client.query(
      "SELECT id, balance FROM accounts WHERE id = ANY($1) ORDER BY id FOR UPDATE",
      [ids],
    );
    const from = rows.find(r => r.id === fromId)!;
    if (from.balance < amount) throw new Error("Insufficient funds");

    await client.query("UPDATE accounts SET balance = balance - $1 WHERE id = $2", [amount, fromId]);
    await client.query("UPDATE accounts SET balance = balance + $1 WHERE id = $2", [amount, toId]);
    await client.query("COMMIT");          // locks are released here
  } catch (e) {
    await client.query("ROLLBACK");
    throw e;
  } finally {
    client.release();
  }
}
Mệnh đềKhóaDùng khi
FOR UPDATEKhóa độc quyền dòngSẽ sửa hoặc xóa dòng
FOR NO KEY UPDATENhư trên nhưng vẫn cho bảng khác tham chiếu khóa ngoạiSửa cột không phải khóa; nhẹ hơn FOR UPDATE
FOR SHAREKhóa chia sẻ: nhiều bên cùng đọc, cấm sửaCần chắc dòng không đổi trong lúc dùng

Lock chỉ sống trong transaction. Gọi FOR UPDATE ngoài BEGIN … COMMIT thì khóa nhả ngay sau câu lệnh. Giữ transaction càng ngắn càng tốt: không gọi API bên ngoài, không chờ người dùng khi đang giữ lock.

03NOWAIT & SKIP LOCKED: không đứng chờ

Mặc định FOR UPDATE gặp dòng đang bị khóa thì đứng chờ. Thêm một từ khóa ở cuối để đổi cách hành xử:

Cách viếtGặp dòng đã bị khóa thìDùng khi
FOR UPDATEĐứng chờ tới khi dòng được nhảBắt buộc phải xử lý đúng dòng đó (chuyển tiền)
FOR UPDATE NOWAITBáo lỗi ngay (mã 55P03)Báo người dùng “ghế này đang có người đặt”
FOR UPDATE SKIP LOCKEDBỏ qua, lấy dòng khác còn trốngDòng nào cũng được, miễn chưa ai nhận: job queue, phát mã giảm giá
 
// NOWAIT: fail immediately if someone else holds the lock
try {
  await client.query("SELECT * FROM seats WHERE id = $1 FOR UPDATE NOWAIT", [seatId]);
} catch (e: any) {
  if (e.code === "55P03") throw new Error("Seat is being booked by someone else");
  throw e;
}

// Bounded wait instead of waiting forever
await client.query("SET LOCAL lock_timeout = '2s'");

SKIP LOCKED: nhiều worker chia nhau một bảng việc

Ba worker chạy cùng một câu lệnh lấy 3 job. Worker A khóa job 1–3; worker B gặp 1–3 đang bị khóa nên bỏ qua và lấy 4–6; worker C lấy 7–9. Không ai nhận trùng, không ai phải chờ.

Cách 1: giữ transaction trong lúc xử lý

async function workOnce(): Promise<number> {
  const client = await pool.connect();
  try {
    await client.query("BEGIN");
    const { rows: jobs } = await client.query(`
      SELECT id, payload FROM jobs
      WHERE status = 'pending'
      ORDER BY created_at
      LIMIT 10
      FOR UPDATE SKIP LOCKED
    `);
    for (const job of jobs) {
      await handle(job.payload);                        // must be short
      await client.query("UPDATE jobs SET status = 'done' WHERE id = $1", [job.id]);
    }
    await client.query("COMMIT");                       // locks released, rows done
    return jobs.length;
  } catch (e) {
    await client.query("ROLLBACK");                     // jobs go back to pending automatically
    throw e;
  } finally {
    client.release();
  }
}

Đơn giản và an toàn: worker chết giữa chừng thì transaction rollback, job tự quay về pending. Nhược điểm là giữ connection và lock suốt thời gian xử lý, nên chỉ hợp với việc ngắn.

Cách 2: nhận việc nhanh, xử lý ngoài transaction

// Claim a batch in one short statement, then process without holding locks
const { rows: jobs } = await pool.query(`
  UPDATE jobs SET status = 'processing', locked_by = $1, locked_at = now()
  WHERE id IN (
    SELECT id FROM jobs
    WHERE status = 'pending'
    ORDER BY created_at
    LIMIT 10
    FOR UPDATE SKIP LOCKED
  )
  RETURNING id, payload
`, [workerId]);

for (const job of jobs) {
  await handle(job.payload);                            // can be slow: no lock held now
  await pool.query("UPDATE jobs SET status = 'done' WHERE id = $1", [job.id]);
}

// Reaper: return jobs stuck in "processing" (worker crashed) to the queue
await pool.query(`
  UPDATE jobs SET status = 'pending', locked_by = NULL
  WHERE status = 'processing' AND locked_at < now() - interval '5 minutes'
`);

Hợp với việc chạy lâu. Đổi lại phải có tiến trình dọn job bị kẹt, và việc xử lý nên idempotent vì một job có thể bị chạy lại sau khi bị trả về.

Hay dùng choJob queue trong PostgreSQL (pg-boss, Graphile Worker, Solid Queue), chia đơn hàng cho nhiều instance, phát mã giảm giá hoặc vé có hạn, xử lý bảng outbox bằng nhiều relay.
Lưu ýKết quả cố tình bỏ sót dòng bị khóa: không dùng để đọc báo cáo hay đếm. Phải nằm trong transaction. Cần index trên cột lọc (status, created_at). Hỗ trợ từ PostgreSQL 9.5 và MySQL 8.0.

04Deadlock

Transaction A khóa dòng 1 rồi chờ dòng 2; transaction B khóa dòng 2 rồi chờ dòng 1. Cả hai chờ nhau mãi. PostgreSQL phát hiện sau deadlock_timeout (mặc định 1 giây) và hủy một bên với lỗi 40P01.

  • Khóa theo thứ tự cố định, ví dụ luôn theo id tăng dần như hàm transfer ở trên.
  • Khóa ít dòng nhất có thể, giữ transaction ngắn.
  • Bắt lỗi deadlock và retry cả transaction.

05Optimistic lock: không khóa, kiểm tra lúc ghi

Giả định xung đột hiếm. Mỗi dòng có cột version. Khi ghi, chỉ cập nhật nếu version vẫn như lúc đọc; nếu người khác đã sửa trước thì không có dòng nào được cập nhật, ta biết có xung đột và làm lại.

async function renameProduct(id: string, newName: string, maxRetries = 3) {
  for (let attempt = 0; attempt < maxRetries; attempt++) {
    const { rows } = await db.query("SELECT name, version FROM products WHERE id = $1", [id]);
    const current = rows[0];

    // Write only if nobody changed the row since we read it
    const res = await db.query(
      "UPDATE products SET name = $1, version = version + 1 WHERE id = $2 AND version = $3",
      [newName, id, current.version],
    );
    if (res.rowCount === 1) return;        // success
    // rowCount 0: someone else won the race, read again and retry
  }
  throw new Error("Conflict: product was modified by someone else");
}
  • Qua HTTP: server trả ETag: "v7", client gửi lại If-Match: "v7" khi PUT; lệch thì trả 412 Precondition Failed (xem tab REST).
  • ORM: JPA @Version, TypeORM @VersionColumn, Prisma dùng điều kiện where: { id, version }.
  • Có thể dùng updated_at thay cho version, nhưng dễ trùng khi hai lần ghi cùng mili giây.
